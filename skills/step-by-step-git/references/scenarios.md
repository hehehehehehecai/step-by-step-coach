# Git 与 GitHub 场景决策参考

本文件供 `step-by-step-git` 内部按需读取。它是状态决策地图，不是给用户一次性照做的步骤清单。每次只取当前状态对应的一个观察或动作。

## 通用决策原则

- 先确定最终目标，再确认当前状态。
- 优先选择不会改变仓库的最小只读检查。
- 一个命令或一个网页动作独占一轮。
- 用户反馈与预期不一致时停止原路线，重新判断。
- 任何高风险动作先返回主 Skill 的风险确认门禁。
- 所有示例中的占位符必须替换为用户已经确认的真实值；未知时先询问，不猜测。

## 首次把本地项目上传到 GitHub

判断重点：

- 当前 PowerShell 所在目录是否真的是目标项目；
- 是否已经是 Git 仓库；
- 工作区有哪些未跟踪或已修改文件；
- 是否存在 `.gitignore`，待上传内容是否包含敏感文件或异常大文件；
- 是否已有提交、当前分支和远端；
- GitHub 上目标仓库是否已创建、是否为空。

安全顺序是先确认目录和文件范围，再确认本地仓库状态，然后才进入提交、远端和推送。发现 `.env`、私钥、Token、数据库或大文件迹象时停止正常路线，先处理敏感内容。

成功信号：目标 GitHub 仓库中可见预期分支和提交，且上传内容经过用户核对。

## 已有修改的提交与推送

先区分未跟踪、已修改、已暂存和已提交。一次只确认一个状态或完成一个动作。

不要把 `add`、`commit`、`push` 合并。提交前确认暂存内容，推送前确认当前分支和远端。存在意外文件时先停止。

成功信号：提交存在于预期分支，远端显示相同提交。

## 推送当前分支

判断是否存在上游分支、远端地址是否正确、当前分支是否是用户希望推送的分支。远端拒绝时先读取完整报错。

遇到 non-fast-forward：优先查明远端新增内容；不得直接建议 force push。

成功信号：Git 输出明确显示推送完成，或远端页面能看到该分支的最新提交。

## 创建功能分支

先确认当前分支、工作区是否干净以及新分支用途和名称。名称未知时只询问，不代替用户决定。

成功信号：当前分支切换到目标分支，且用户现有修改未丢失。

## 创建 Pull Request

默认使用 GitHub 网页。先确认：

- 功能分支已经推送；
- base 和 compare 分支；
- 页面是否已经存在同一分支的 PR；
- 标题、描述和检查状态是否准备好。

每轮只指导一个页面动作，例如打开提示链接、选择 base、填写标题、填写描述或点击创建。点击“Create pull request”属于创建外部状态，必须让用户亲自操作。

成功信号：PR 页面已生成且 base/compare 正确。

## 更新已有 Pull Request

先确认 PR 对应的源分支和当前本地分支。普通新增提交推送到同一源分支后，PR 通常自动更新；仍须以页面或远端结果验证。

成功信号：PR 页面出现目标新提交或预期变更。

## 拉取远端更新

先确认工作区状态、当前分支和远端跟踪关系。存在未提交修改时先保护它们，不直接 pull。

如果 pull 产生分歧或冲突，停止原路线并进入相应场景。

成功信号：本地分支包含预期远端提交且工作区状态明确。

## 合并 Pull Request

合并会改变目标分支，属于高风险网页操作。先确认：

- base 分支正确；
- 审查和检查状态；
- 合并方式；
- 是否需要保留源分支。

必须先独立说明影响并取得明确确认，下一轮才指导一个合并页面动作。

成功信号：GitHub 明确显示 PR 已合并，目标分支包含对应提交。

## 工作区存在未提交修改

先识别修改属于用户当前任务还是意外残留。不得默认丢弃、暂存或提交。若要切分提交，一次只处理一个文件范围或状态检查。

任何丢弃修改的动作都进入高风险门禁。

## 合并冲突

先确定冲突发生在 merge、rebase、pull 还是 cherry-pick，并确认当前 Git 状态。一次只处理一个冲突观察、一个文件编辑要求或一个继续/中止动作。

中止、继续和重置可能影响现有工作，必须依据当前状态解释后再决定；不得同时给出多个选择命令。

成功信号：冲突标记消失、Git 状态明确，且目标操作完成或安全中止。

## 认证、权限、远端和分支名错误

常见观察：

- 命令不存在：确认 Git 是否安装；
- authentication failed：判断当前认证方式，但不索取凭据；
- permission denied：确认仓库权限与账号；
- repository not found：确认远端地址和可见性；
- no upstream branch：确认用户要关联的远端和分支；
- src refspec does not match：确认本地分支、提交和拼写；
- remote already exists：读取现有远端，不直接覆盖。

每次只针对报错原文选择一个检查。不得要求用户粘贴 Token、密码或私钥。

## Force push 与历史重写

无论用户多着急，都先说明：

- 将影响哪个远端分支或哪些提交；
- 其他人的提交可能被覆盖；
- 更安全的替代方案，例如先拉取、比较或建立备份分支；
- 需要用户明确确认。

确认前禁止给出 force push、hard reset、rebase 或 amend 的具体执行命令。确认后仍需先确保目标分支和远端已经被验证。
